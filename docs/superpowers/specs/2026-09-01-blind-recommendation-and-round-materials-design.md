# 盲评推荐结论与分轮资料清单设计

## 目标

基于当前验收版本，调整评委权限、盲评推荐结论、特别推荐票和分轮资料检查，同时保持现有项目评分完成度、评分算法，并适配 PostgreSQL 直连主线。

## 范围与基线

- 开发基线：`codex/project-pool-v2`，对应当前 Vercel 验收版本。
- 数据库：生产主线使用 PostgreSQL 直连仓储；迁移脚本保持 PostgreSQL 兼容。
- 评委名单：只读取现有 `reviewers` 表和评审会的 `meeting_reviewers` 快照中的非管理员账号，保持实际已有的 7 名评委，不新增 Nadia 或其他账号。
- Walker 仍保留本轮加分权限，但不再拥有特殊结论或最终评级控件。
- 现有普通评分输入、评分完成度、总分和维度换算逻辑保持不变。

## 评委端行为

### 个人评分与盲评

所有当前评审会快照中的非管理员评委均可：

- 填写当前轮次所有评分项；
- 填写本轮个人项目评级 S/A/B/C；
- 填写本轮个人结论：通过、重评、驳回；
- 填写存在问题和整改意见；
- 在页面底部选择或取消“特别推荐票”。

Walker 只额外显示本轮 0-5 分加分项及加分原因，不显示最终结论或最终评级选择。

特别推荐票使用当前评审会、当前项目、当前轮次和当前评委作为唯一范围，保存为当前状态；页面强调“半年只有一票”，但系统不做次数校验。结论与报告显示特别推荐票标记及投票评委名单。

### 完成度

项目评分完成度继续只统计当前评审会、当前轮次的正常评分项，沿用现有分子、分母和四舍五入规则。个人评级、个人结论、特别推荐票、问题、整改意见和资料检查均不计入评分完成度。

## 推荐结论

推荐结论只基于已提交的个人结论，缺席评委不计入分母：

1. 已提交结论数量为 0 时，显示“待形成建议”。
2. 通过票数大于已提交票数的一半时，推荐“通过”。
3. 通过未过半，或通过票与非通过票平局时，进入非通过票二次判断。
4. 重评票数大于等于非通过票数的一半时，推荐“重评”；否则推荐“驳回”。

例如已提交 3 票，其中通过 1、重评 1、驳回 1，则通过未过半，重评达到非通过票的一半，推荐重评。

### 管理员覆盖

- 结论与报告页面默认展示实时推荐结论，不写入管理员覆盖值。
- 管理员选择“跟随推荐”时清除覆盖值，页面继续随盲评数据变化。
- 管理员选择通过、重评或驳回时，写入当前评审项目和轮次的管理员覆盖值，页面显示该人工结论。
- 报告快照生成时重新读取最新汇总，以当前管理员覆盖值优先，否则使用实时推荐结论。
- 旧的 Walker 结论记录保留作为历史数据，但新版结果页和报告不再单独展示 Walker 结论，也不使用其推动项目状态流转。

## 数据设计

### 现有 `scores` 表中的特殊记录

继续复用现有评分表，新增以下特殊维度键：

- `r1::__admin_verdict__`、`r2::__admin_verdict__`：管理员结论覆盖，`comment` 为 `approved`、`recheck`、`rejected` 或空值。
- `r1::__special_vote__`、`r2::__special_vote__`：特别推荐票，`score=1` 表示已投，`score=0` 表示取消。

个人结论继续使用 `r1::__verdict__`、`r2::__verdict__`，但统计范围改为当前评审会快照中的全部非管理员评委，包括 Walker。

### 分轮资料

`project_materials` 增加 `round_no` 字段，并将业务唯一键调整为 `project_id + round_no + item_key`。旧记录保留，迁移脚本不得依赖不存在的 `id` 列。

第一轮“创意评审资料”：

| 资料项 | 必填 |
|---|---|
| 项目基础信息 | 是 |
| 项目定位 | 是 |
| 产品/玩法方案 | 是 |
| MVP 制作计划 | 是 |
| 竞品或参考 | 否 |

第二轮“立项评审资料”：

| 资料项 | 必填 |
|---|---|
| 项目基础信息 | 是 |
| 风险说明 | 是 |
| 可体验 MVP 版本 | 是 |
| 项目预算与排期计划 | 是 |
| MVP 版本说明 | 是 |
| 虚拟团队资源配置（初步） | 否 |
| 商业模式规划 | 否 |
| 资源需求 | 否 |
| 竞品或参考 | 否 |

资料状态只保留缺失、待完善、已提交、豁免；已提交和豁免均视为该资料项齐全。旧的运营指标等历史记录保留但不再作为新清单项目展示或计入新清单必填判断。

## 服务端数据流

1. 评分 API 校验当前登录评委属于当前评审会非管理员快照。
2. 普通评分照旧校验评分项和评分范围。
3. 个人结论允许所有非管理员写入，取消 Walker 专属状态流转。
4. 管理员只能写入管理员结论覆盖特殊键；评委不能写入该键。
5. 特别推荐票允许所有非管理员写入 0/1，管理员不参与投票。
6. 汇总 API 同时返回推荐结论、管理员覆盖状态、盲评结论统计、盲评评级统计、特别推荐票明细和现有评分完成度。
7. 报告构建统一消费汇总 API 的最终展示结论，确保实时页和快照页使用同一套优先级。

## 页面变更

- 评委页面：Walker 与其他评委使用相同的个人评级、个人结论区；移除 Walker 最终结论和最终评级；底部增加红色特别推荐票。
- 管理员结论与报告页面：显示推荐结论、盲评数量/比例、特别推荐票及评委；增加“跟随推荐/手动结论”控制。
- 实时汇总与两类评审报告：移除 Walker 结论表头和文案，改为推荐结论；保留项目总分、维度平均分、完成度、问题与行动等现有内容。
- 项目详情资料检查：按当前项目评审轮次切换对应清单，显示真实保存状态。

## 错误处理

- 资料项或轮次不在当前定义中时返回明确的中文错误，不写入数据。
- 管理员覆盖只能写入三个合法结论或清除；非法值返回 400。
- 特别推荐票只接受 0 或 1；越权账号返回 403。
- 资料迁移遇到旧表缺少 `id` 时仍可执行，使用业务键和现有字段完成迁移。
- 报告没有盲评结论时显示“待形成建议”，不得伪造通过、重评或驳回。

## 测试与验收

自动化测试覆盖：

- 7 名评委来源于现有快照，不创建 Nadia；
- Walker 与其他评委拥有相同的个人结论和评级权限；
- 推荐结论的过半、平局、重评临界值、驳回和缺席场景；
- 管理员覆盖优先级及清除覆盖后恢复推荐；
- 特别推荐票的投票、取消、名单汇总；
- 两轮资料清单及必填完整度；
- 原有评分完成度计算结果不变；
- 报告不出现 Walker 结论，且快照使用最新推荐或管理员覆盖。

验收流程：先运行测试和构建，再检查评委端、管理员汇总、报告快照和资料检查。通过验收后同步 GitHub 与公司 GitLab 的 `main`，并确认 PostgreSQL 迁移已执行。
